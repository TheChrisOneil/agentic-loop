Agent Loop: one nightly tick of supplier invoices

repo thechrisoneil/agentic-loop path course/demo/ 526 lines of shell in steps, lib, scripts 2026-09-24

Purpose Explain what the demo agent loop does, using UML diagrams grounded in the repository code.

EX The loop is a nine-step shell pipeline. Code decomposes, matches, gates, verifies, proves and delivers; a model makes exactly one judgment per unit (5-judge.sh). make tick yields 9 units: 2 closed by rule, 3 refused, 4 proposed, 0 failed, 0 tokens.

1. Scope

course/demo/ reconciles supplier invoices against purchase orders. The unit of work is (supplier, purchase order): the smallest thing that gets one decision (steps/1-decompose.sh:6-10).

1 decompose code→ 2 match code→ 3 select code→ 4 gate gate→ 5 judge model→ 6 verify test→ 7 gate gate→ 8 prove code→ 9 gate + deliver gate

Stage legend from loop.sh:4-5. Steps 1-3 run once per tick; steps 4-9 run once per selected unit.

Measured with make tick, JUDGE_MODE=stub (recorded answers, zero tokens).

2. Activity diagram: one tick

Each refusal or failure exits that unit only; the loop continues with the next (loop.sh:26-32).

flowchart TD
  A([tick]) --> D[1 decompose: lines to units, key supplier + PO]
  D --> M[2 match: arithmetic + injection screen, classify]
  M --> S[3 select: sort by exposure, cap at BUDGET]
  S -->|clean, within_tolerance| CR([closed_by_rule])
  S -->|over budget| DF([deferred])
  S -->|per unit| G1{4 gate_pre}
  G1 -->|no_po, injection_suspect, supervised| RF([REFUSED.md + next human action])
  G1 -->|proceed| J[[5 judge: the one model step]]
  J --> V{6 verify: recompute to the cent}
  V -->|mismatch| FL([failed + trust fail])
  V -->|match| G2{7 gate_post: 4 checks}
  G2 -->|fail| RF
  G2 -->|pass| P[8 prove: proof.txt + sha256]
  P --> G3{9 deliver: checksum intact?}
  G3 -->|edited| BL([blocked])
  G3 -->|intact| PR([PROPOSAL to named approver])

4. State machine: unit lifecycle

The loop never approves its own work: "It never approves its own work, on any day, at any trust tier" (9-deliver.sh:5).

stateDiagram-v2
  [*] --> Classified: decompose + match
  Classified --> ClosedByRule: clean or within_tolerance
  Classified --> Deferred: beyond BUDGET
  Classified --> Selected
  Selected --> Refused: gate_pre
  Selected --> Judged
  Judged --> Failed: verify mismatch
  Judged --> Verified
  Verified --> Refused: gate_post
  Verified --> Proved
  Proved --> Blocked: checksum mismatch
  Proved --> Proposed
  Proposed --> [*]: human approves or rejects, outside the loop

5. Class view: the judge seat

All three modes write the same four field TSV: call, adjustment, evidence, next_action (5-judge.sh:35-54). Downstream steps cannot tell them apart.

classDiagram
  class JudgeSeat { <<interface>> +judge(unit) judgment.tsv }
  class StubJudge { replays judgments.stub.tsv; 0 tokens }
  class HumanJudge { reads stdin }
  class ClaudeJudge { claude -p --model JUDGE_MODEL }
  class Verifier { +recompute(unit) }
  JudgeSeat <|.. StubJudge
  JudgeSeat <|.. HumanJudge
  JudgeSeat <|.. ClaudeJudge
  Verifier ..> JudgeSeat : distrusts output

8. HIPAA relevance

inference These properties transfer to a PHI workflow: an append only audit trail, tamper evident proof, a zero token deterministic default, a named human approver, and rule based injection screening before model exposure.

ClaudeJudge needs a BAA covered model endpoint and PHI minimization in the prompt before adoption.
